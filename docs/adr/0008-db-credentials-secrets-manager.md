# ADR-0008. Пароль базы TimeCapsule в AWS Secrets Manager

## Статус: принято

## Контекст

Приложение TimeCapsule подключается к PostgreSQL под ролью `timecapsule`.
До индивидуальной работы пароль этой роли лежал в `.env` на сервере
`timecapsule-dev-app`, а образ ЛР6 создаётся как копия корневого диска этого
сервера. Поэтому пароль попадал в каждый новый AMI, в два старых AMI
(`timecapsule-dev-app-lab2`, `timecapsule-dev-app-lab6`), в переменные
окружения Lambda mailer/opener и в локальный state ЛР7. Пароль был длиной
**3 символа**.

Шифрование RDS на уровне хранения (`storage_encrypted`) не решает проблему:
приложение само подключается с этим паролем, а любой, кто получил AMI или
state, получает рабочий доступ к базе. Ротация требовала вручную обновить
сервер, оба AMI и две Lambda, поэтому на практике не выполнялась.

Метрика до изменений: **число AMI с действующим паролем БД** и длина пароля.
В аккаунте было два self-owned AMI; самый новый `timecapsule-dev-app-lab6`
создан из текущего `timecapsule-dev-app` и содержал действующий пароль.
Итого: **1/1 актуальный AMI с рабочим паролем, 3 символа, 6 известных копий**
(сервер, два AMI, две Lambda, state). После ротации старый пароль проверен
через `psql`: `password authentication failed`.

## Решение

Пароль роли `timecapsule` хранится в секрете AWS Secrets Manager
`timecapsule-dev-db`. Приложение читает ARN из переменной `DB_SECRET_ARN`,
получает `SecretString` через `secretsmanager:GetSecretValue` и кэширует
пароль в tmpfs (`/dev/shm`) на 300 секунд. В `.env` и AMI остаются только
несекретные параметры: хост, порт, имя БД, пользователь и ARN секрета.
Ключей доступа нет: SDK использует временные учётные данные instance role
`timecapsule-dev-app-role`.

Права выдаёт отдельная customer-managed policy
`timecapsule-dev-app-secretsmanager`: одно действие `GetSecretValue` только
на ARN секрета, с условиями `aws:RequestedRegion = eu-central-1` и
`aws:SecureTransport = true`. Для упражнения B4 в этой же policy
переключателем OpenTofu включается явный `Deny`; после проверки возвращается
`Allow`.

Пароль ротирован на случайные **43 символа**. Новый AMI
`timecapsule-dev-app-individual-20261127` собран после удаления
`DB_PASSWORD` из `.env`; старые AMI содержат только недействительный старый
пароль. Lambda mailer/opener обновлены на новый пароль через их OpenTofu
стек; это остаётся отдельной копией, которую нужно убрать при следующем
шаге (например, тоже через Secrets Manager).

## Рассмотренные альтернативы

| Критерий | Как есть | Без нового сервиса: RDS IAM authentication | Secrets Manager |
| --- | --- | --- | --- |
| Стоимость при учебной нагрузке | $0 дополнительно | $0 дополнительно | ~$0.40 за секрет + несколько центов за вызовы |
| Стоимость при 10 000 пользователей | $0 | $0 | ~$0.49/мес при 200 000 запросов и кэше 300 с; ~$1.40/мес без кэша |
| Что поддерживать | 6 копий пароля, ручная ротация, нет аудита | RDS IAM auth, роль БД `rds_iam`, TLS, генерация token на каждое подключение | IAM policy, секрет, кэш, обработка ошибок, ротация |
| Скорость для пользователя | 0 мс на чтение пароля | ~10–30 мс на генерацию token при новом подключении | 0–1 мс из кэша; 138–346 мс холодное чтение раз в 300 с |
| Безопасность и данные | 3-символьный пароль в AMI, state и Lambda | Пароля нет; token живёт 15 минут; доступ определяется IAM | Пароль 43 символа, шифрование, IAM, аудит; пароль есть в памяти и tmpfs |
| Что переписать при переезде из AWS | ничего | сменить IAM-провайдер и способ выпуска token | заменить адаптер `src/secrets.php` на Vault/SSM; env и логика остаются |
| Сложность разработки и выпуска | низкая | средняя: изменить RDS, роль БД и подключение PDO | средняя: политика, секрет, кэш, AMI + ASG, обработка 500 |

RDS IAM authentication — сильный вариант без нового сервиса: он вообще
убирает статический пароль. Но он требует включить IAM auth на RDS,
создать роль с `rds_iam`, всегда использовать TLS и генерировать token на
каждое новое подключение. В текущем приложении PDO создаётся на запрос,
поэтому это добавило бы задержку к каждому запросу и изменило бы не только
код, но и параметры RDS. Secrets Manager выбран потому, что он убирает
пароль из AMI без изменения RDS, даёт аудит и ротацию, а стоимость при
учебной нагрузке пренебрежимо мала.

## Плюсы выбранного решения

- Один источник пароля вместо шести копий; в новом AMI и `.env` пароля нет
  (проверено `grep -c '^DB_PASSWORD=' .env` → `0`).
- Пароль стал 43 символа вместо 3; старый пароль после ротации отвергается
  PostgreSQL (`password authentication failed`).
- Права минимальны: одно действие и один ARN, без `ListSecrets`,
  `DescribeSecret` и без доступа к другим секретам.
- Ключей доступа нет: приложение использует instance role и IMDSv2.
- Секрет читается из кэша за 0–1 мс; холодное чтение 138–346 мс происходит
  раз в 300 с на инстанс, а не на каждый запрос.
- Ротация и аудит выполняются в одном месте; старые AMI автоматически
  становятся бесполезны после смены пароля.

## Минусы выбранного решения

- Secrets Manager стал частью главного пути. При отказе `GetSecretValue`
  приложение возвращает HTTP 500, ALB помечает target как unhealthy,
  `/health` показывает `credentials: error`. Это честная деградация:
  без пароля нельзя открыть БД, но статика, error page и фоновые Lambda
  продолжают работать.
- Кэш 300 с и eventual consistency IAM задерживают обнаружение сбоя: в B4
  один инстанс ещё отдавал закэшированный пароль, пока другой уже получал
  `AccessDeniedException`. Для продакшена нужен меньший TTL (например, 60 с)
  или отдельный no-cache health probe/канарейка.
- Lambda mailer/opener по-прежнему получают пароль через environment
  variables; это две оставшиеся копии. Их нужно перевести на Secrets Manager
  отдельным изменением.
- Секрет хранится в локальном OpenTofu state; state и `.tfvars` исключены
  из Git, но их нужно защищать. Стоимость $0.40/мес за секрет существует
  независимо от числа запросов.

## Последствия и условия пересмотра

- B4: после замены `Allow` на `Deny` приложение отдаёт 500 с понятным
  сообщением; ALB target health становится `unhealthy`
  (`Target.ResponseCodeMismatch`); CSS отдаётся с 200; Lambda opener всё
  равно открывает капсулу (`openedCount: 1`), потому что использует свой
  пароль. После возврата `Allow` и замены инстансов `/health` снова 200.
- Ротация: сначала сменить пароль роли в PostgreSQL, затем версию секрета
  в OpenTofu, затем очистить tmpfs-кэш/перезапустить PHP-FPM и обновить
  Lambda. Старые AMI и снимки после этого не дают доступа.
- Пересмотреть решение, если появятся требования к HSM/строгому аудиту,
  если захочется убрать последние копии в Lambda (тогда Secrets Manager
  для Lambda или RDS IAM auth), или если стоимость вызовов при очень
  высокой нагрузке станет заметной. При переезде из AWS достаточно
  заменить `src/secrets.php` на адаптер Vault/SSM; остальной код не меняется.
- Если платить за аккаунт самостоятельно, решение всё равно оправдано:
  $0.49/мес при 10 000 пользователях — меньше стоимости одного часа
  t3.micro. При почти нулевой нагрузке и нежелании зависеть от AWS
  разумнее RDS IAM authentication или Vault.
