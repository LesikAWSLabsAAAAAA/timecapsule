# ADR-0005. Хранение сессий TimeCapsule

## Статус: принято

## Контекст

Группа Auto Scaling запускает несколько серверов приложения и может заменить любой из них. Раньше PHP хранил сессии файлами на диске одного сервера: при переходе на другой сервер вход терялся.

## Решение

Хранить сессии в таблице DynamoDB `timecapsule-dev-sessions` в режиме on-demand. PHP использует `Aws\DynamoDb\SessionHandler`, таблица имеет строковый ключ `id` и TTL по полю `expires`. Сервер получает временные учётные данные от своей IAM-роли, которой разрешены операции с этой таблицей; ключи доступа в `.env` не записываются. TTL удаляет просроченные записи асинхронно, а не точно в момент истечения.

## Рассмотренные альтернативы

| Вариант | Преимущество | Недостаток |
| --- | --- | --- |
| Файлы и sticky sessions ALB | Почти не нужно менять приложение | Привязка направляет пользователя к прежнему серверу, пока он доступен; при его замене локальная сессия теряется. |
| Таблица сессий в RDS | Одна знакомая СУБД и SQL | Дополнительная нагрузка на общую базу; остановка или отказ RDS затрагивают и сессии. |
| DynamoDB | Общее хранилище для всех серверов, TTL, не требуется управлять сервером | Дополнительный сервис, IAM-политика и зависимость от доступности DynamoDB. |

## Последствия

- Серверы могут читать одну и ту же сессию независимо от того, какой из них выбрал ALB.
- Учебная конфигурация использует обработчик SDK без блокировок: одновременные изменения одной сессии могут перезаписать друг друга. Для приложения с частыми параллельными изменениями следует отдельно проверить стратегию блокировок и необходимые IAM-разрешения.
- Сессии зависят от сетевого доступа к DynamoDB; потеря доступа к сервису влияет на работу с ними.
- Образ приложения содержит `.env` и секреты подключения к базе: его нельзя публиковать или предоставлять посторонним. Для настоящей эксплуатации секреты лучше хранить отдельно от образа.
