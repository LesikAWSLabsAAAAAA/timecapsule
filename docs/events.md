# События TimeCapsule

## `capsule.sealed`

После записи капсулы приложение публикует в стандартную тему SNS JSON:

```json
{"eventType":"capsule.sealed","capsuleId":123}
```

Подписка SQS фильтрует по телу и включает raw delivery. Потребитель читает
название, время и адрес из базы по идентификатору; содержимое капсулы, пароль
и вложения в сообщении не нужны. Standard SQS допускает повторы, поэтому
запись уведомления защищена уникальным частичным индексом в PostgreSQL.

## Результат открытия

Scheduler асинхронно вызывает `timecapsule-dev-opener`. Успешный вызов
передаётся в SNS как **запись вызова Lambda**, не как исходное тело события.
Внутри записи находятся, например:

```json
{"responsePayload":{"eventType":"capsules.opened","openedCount":2}}
```

Если капсул не открылось, `eventType` равен `capsules.none_opened` и счётчик
равен нулю. Email-подписка фильтрует тело по вложенному
`responsePayload.eventType = capsules.opened`; подписка очереди получает
только `capsule.sealed`. Функция открытия записывает уведомления в одной
транзакции с открытием капсул.

## Ограничения надёжности

Сохранение капсулы и публикация SNS не являются одной транзакцией: при отказе
SNS после записи БД пользователь получит ошибку, но запись может остаться без
события. Также успешный commit открытия и доставка invocation record в SNS не
атомарны: ошибка доставки может оставить капсулу открытой без письма SNS.
Для гарантированной публикации в промышленной системе нужен transactional
outbox с повторной отправкой, наблюдением за ошибками и идемпотентными
потребителями; текущая учебная схема этого не обеспечивает.
