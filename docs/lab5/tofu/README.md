# OpenTofu — ЛР5

Два независимых стека, отдельный локальный state. OpenTofu ≥ 1.11, AWS provider зафиксирован lock-файлами. Целевой регион — `eu-central-1`. VPC, подсети, EC2, существующая SG приложения и зона Route 53 читаются через data sources. Два исключения для управляемых изменений: временная привязка новой SG к ENI `timecapsule-dev-app` и существующая запись `db.timecapsule.internal`, импортированная в state стека приложения.

Оба стека по умолчанию запрашивают `backup_retention_days=1` для AWS Free account plan. Исходные 7 дней можно выбрать через `-var=backup_retention_days=7` только на аккаунте, который их поддерживает. Смена тарифа не нужна для изменения конфигурации и не выполнялась. Фактическая поддержка операций на Free проверяется при запуске.

## Что проверено до развёртывания

В обоих стеках прошли `tofu validate` и `tofu plan`. Сводка первоначальных планов (до первого `apply`), без идентификаторов аккаунта и секретов:

| План | Добавить | Изменить | Удалить | Что входит |
| --- | ---: | ---: | ---: | --- |
| Учебный, по умолчанию | 5 | 0 | 0 | `lab5-db`, subnet group, две SG, привязка SG к ENI |
| Учебный, `create_replica=true` | 6 | 0 | 0 | То же плюс реплика |
| Учебный, `create_restore=true` с демонстрационным временем | 6 | 0 | 0 | То же плюс PITR-копия, без реплики |
| Приложение, по умолчанию | 7 | 0 | 0 | RDS, subnet group, SG, IAM-политика, роль, привязка политики, Scheduler |
| Приложение, `switch_database_dns=true` | 7 | 1 | 0 | То же плюс изменение A → CNAME |

Все строки рассчитаны **до создания RDS**, поэтому условные планы включают и основной экземпляр. После применения предыдущей фазы заново запустить `plan`: ожидается, что план cutover покажет только изменение DNS, если нет посторонних изменений. Демонстрационный PITR-план проверяет конфигурацию, но не доступность момента для восстановления.

```text
# aws_route53_record.db will be updated in-place
~ type = "A" -> "CNAME"
```

У проверенной версии провайдера смена типа отправляет удаление A и создание CNAME одним транзакционным пакетом Route 53. Ранее закэшированный A всё равно может действовать до истечения TTL (300 с).

## Перед первым apply

- `tofu init` и `tofu plan` выполняются отдельно из каждой папки. Пароль `dbadmin` задаётся отдельно для каждого стека в локальном `terraform.tfvars` (`chmod 600`) или через `TF_VAR_db_admin_password`. В AWS аргумент передаётся через `password_wo`; пароль не сохраняется в плане или state. Не публикуйте `.tfvars`, state, планы и журналы.
- Если локальный state `part2-app` уже содержит `aws_route53_record.db`, повторно не импортировать. На новой рабочей копии нужно либо перенести защищённый state, либо, **до первого применения и пока жива старая запись**, импортировать её:

  ```bash
  tofu import aws_route53_record.db '<private-zone-id>_db.timecapsule.internal_A'
  tofu plan
  ```

  План создания RDS должен оставить запись A без изменений. Не запускайте `destroy` для `part2-app`: стек управляет DNS-именем приложения. Перед любым `apply` просматривайте актуальный план.

## Порядок применения после согласования

`run-part2.sh` объединяет Terraform, перенос данных и переключение DNS.
На этом стенде нужны SSH-алиас `app` и запущенная старая БД. Запускайте из `docs/lab5`:

```bash
logs=$(mktemp -d /tmp/opencode/lab5-part2.XXXXXXXX)
bash tofu/run-part2.sh all "$logs"
```

Доступны отдельные этапы `provision`, `migrate`, `cutover`, `smoke` с **одной и той же** папкой логов. `smoke` создаёт тестовую капсулу через HTTP; при включённой авторизации регистрируется тестовая учётная запись. Скрипт не удаляет старый EC2 и не пытается откатить DNS после возможных записей в RDS. Если ошибка произошла на этапе переключения, проверяйте `cutover-apply.txt` и не запускайте nginx, пока PHP не подключается к нужной БД. Проверки Scheduler, stop/start, reboot и вывод старого EC2 из эксплуатации выполняются отдельно.

1. **Учебный стек:** проверить SSH и `psql` на `timecapsule-dev-app`; применить план по умолчанию. После создания и наполнения `notes` включить реплику (`-var=create_replica=true`). По окончании проверки репликации вернуться к `create_replica=false`. Для PITR указать `-var=create_restore=true -var=restore_time=<UTC-RFC3339>` с реальным моментом **до** удаления строк и не позже `LatestRestorableTime`. После проверки убрать restore, применить `-var=enable_deletion_protection=false` и выполнить `destroy` учебного стека.
2. **Стек приложения:** применить план по умолчанию с `switch_database_dns=false`. Проверить Scheduler и вернуть расписание на 23:00. Запустить старую БД к миграции. Создать роль и БД в RDS, закрыть доступ обычным запросам к приложению на время переноса, сделать дамп и восстановить данные по **прямому** имени RDS. Сверить количества строк. Перед переключением проверить TLS, в том числе через `\conninfo`. `timecapsule-dev-app` — основной сервер, его не пересоздаём. У существующей `web-sg` есть и другие участники: правило SG разрешает трафик от группы, а не от одного уникального EC2.
3. **Переключение:** после проверки заново построить план с `-var=switch_database_dns=true` и применить его. Зафиксировать `switch_database_dns = true` в локальном `terraform.tfvars` после перехода, чтобы обычный план не возвращал A. Проверить DNS, `/health` и тестовую запись в RDS, прежде чем открыть доступ к приложению. Затем остановить старый `timecapsule-dev-db`, проверить независимость приложения и отдельно согласовать его удаление.
4. **Откат:** пока RDS не принимала новые пользовательские записи, можно закрыть входящий трафик к приложению, убедиться, что старый сервер вновь доступен, и вернуть A через `switch_database_dns=false`. После появления новых записей нельзя просто переключить DNS назад: сначала согласовать сохранение или перенос этих изменений, чтобы не потерять данные.
